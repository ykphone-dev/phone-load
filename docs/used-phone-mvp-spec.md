# 옆커폰 중고폰 거래 플랫폼 MVP 개발 기획서 v1.0

> 원문 기획서. 구현 상태와 실행 방법은 [used-phone-mvp-setup.md](./used-phone-mvp-setup.md) 참고.

## 1. 프로젝트 목적

**한 줄 정의**: 중고폰 사업자가 자신의 상품을 등록하고, 소비자가 상품을 선택해 판매자 계좌로 직접 송금한 뒤 배송받을 수 있는 중고폰 거래 플랫폼.

**MVP의 목표**: 증명해야 할 것은 단 하나다. *"중고폰 판매자들이 실제 상품을 등록하고 소비자가 실제 돈을 보내 구매하는가?"*

초기 집중 기능: 판매자 입점 → 중고폰 상품등록 → 소비자 상품조회 → 주문 생성 → 판매자 계좌안내 → 계좌이체 → 판매자 입금확인 → 배송 → 구매완료 → 취소·환불·분쟁접수

## 2. MVP 핵심 원칙

**원칙 1. 플랫폼은 돈을 받지 않는다.** 소비자 → 판매자 사업자계좌 직접 입금. 플랫폼은 판매대금을 보관하거나 정산하지 않는다. 따라서 PG 결제, 카드결제, 플랫폼 정산, 판매대금 보관, 판매자 출금, 플랫폼 지갑, 포인트, 예치금은 만들지 않는다.

**원칙 2. 사업자 판매자만 입점.** 개인판매자는 받지 않는다. 가입 필수정보: 상호, 대표자명, 사업자등록번호, 통신판매업 신고번호, 사업장 주소, 담당자 이름/휴대폰, 판매대금 입금 은행/계좌번호/예금주, 사업자등록증, 통신판매업 신고증. 관리자가 승인해야 판매 가능.

## 3~5. 사용자 종류

- **소비자**: 상품검색·상세보기·주문·판매자 계좌 확인·입금완료 표시·배송조회·주문취소 요청·환불 요청·분쟁접수. 회원가입은 선택, 비회원 구매 허용 (이름·휴대폰·배송주소·비밀번호).
- **판매자** (별도 Seller 페이지): 회원가입, 사업자 인증신청, 상품등록/수정/판매중지, 주문조회, 입금확인, 배송정보 입력, 취소 승인, 환불처리, 판매현황.
- **관리자**: 판매자 관리(입점신청 조회, 사업자등록증 확인, 승인/정지, 계좌정보 확인), 상품 관리(조회, 강제 판매중지, 신고상품), 주문 관리(전체 조회, 상태, 분쟁상태), 분쟁 관리(소비자 접수, 판매자 답변, 관리자 메모, 처리완료).

## 6~10. 상품 등록 구조

상품 상태를 표준화한다. 판매자가 마음대로 설명하게 하면 분쟁이 발생하므로 필드를 강제한다.

- **기본정보**: 브랜드(Apple/Samsung/기타), 모델, 용량(128GB/256GB/512GB/1TB), 색상, 가격, 판매수량
- **외관등급**: S(거의 새제품) / A(미세한 사용감) / B(생활기스) / C(찍힘·스크래치)
- **액정**: 깨끗함/미세기스/생활기스/찍힘/파손 · **프레임**: 깨끗함/미세기스/찍힘 · **후면**: 깨끗함/기스/파손
- **기능 상태** (정상/이상): 카메라, 전면카메라, Face ID/지문, 스피커, 마이크, 충전, 무선충전, Wi-Fi, Bluetooth, GPS, 진동, 버튼, 디스플레이
- **추가정보**: Apple 배터리 성능 % / Samsung 배터리 상태(좋음/보통/교체권장), 수리이력(없음/있음/모름), 부품교체(없음/있음/모름, 있음 시 내용), 분실·도난 아님 체크(필수), 정상해지(가능/불가능/확인필요), 선택약정(가능/불가능/확인필요), IMEI(관리자/판매자만, 소비자에게 전체 미노출)
- **사진**: 최소 5장 권장 (전면·후면·좌측·우측·액정 필수, 모서리·찍힘·흠집·구성품 선택), 최대 15장

## 11. 상품 상태

`DRAFT` 작성중 → `ON_SALE` 판매중 → `RESERVED` 주문 발생 → `SOLD` 판매완료 / `STOPPED` 판매중지 / `DELETED` 삭제. 1대짜리 상품은 주문 발생과 동시에 일정 시간 RESERVED.

## 12~15. 구매 Flow와 입금 처리

1. 상품 상세 → 구매하기 → 주문정보 입력(구매자명, 휴대폰, 주소, 배송메모) → 최종 확인("판매계약 당사자는 상품 판매자입니다. 옆커폰은 통신판매중개 플랫폼입니다.") → 주문 생성 (`ORDER-20260909-000123`)
2. 계좌이체 화면: 입금 금액, 판매자, 은행, 계좌, 예금주 + 계좌번호 복사 / 입금했습니다 버튼. 주의문구: "판매자 명의 계좌인지 확인하세요. 옆커폰은 판매대금을 보관하지 않습니다."
3. 소비자가 "입금했습니다" 클릭 → `WAITING_DEPOSIT` → `DEPOSIT_REPORTED`. 판매자가 실제 계좌 확인 후 "입금 확인" → `DEPOSIT_CONFIRMED`.
4. **가장 중요한 원칙**: 소비자의 "입금했습니다"와 판매자의 "실제 입금 확인"은 반드시 분리한다. 절대로 소비자의 버튼만으로 배송단계로 넘어가면 안 된다.

## 16. 주문 상태

`CREATED`, `WAITING_DEPOSIT`, `DEPOSIT_REPORTED`, `DEPOSIT_CONFIRMED`, `PREPARING`, `SHIPPED`, `DELIVERED`, `COMPLETED`, `CANCEL_REQUESTED`, `CANCELLED`, `REFUND_REQUESTED`, `REFUNDED`, `DISPUTED`

## 17. 미입금 주문 처리

주문 후 30분간 상품은 RESERVED. 입금완료 표시가 없으면 주문 자동취소, 상품 ON_SALE 복귀. 관리자가 시간 설정 가능.

## 18~22. 배송 / 구매완료 / 취소 / 환불 / 분쟁

- **배송**: 판매자 입금확인 후 택배사·송장번호·배송일 입력 → `SHIPPED`. 소비자 배송조회.
- **구매완료**: 배송완료 후 소비자 구매확정 → `COMPLETED`. MVP에서는 돈 지급과 연결되지 않는 상태 기록.
- **취소**: 입금 전 즉시 취소. 입금 후는 판매자 확인 필요(`CANCEL_REQUESTED` → 판매자 환불 후 `CANCELLED`).
- **환불**: 사유(상품 상태 다름/기기 불량/파손/오배송/구성품 누락/단순변심/기타) + 사진. 환불은 판매자가 소비자 계좌로 직접 처리 → 판매자 "환불 완료" → 소비자 "환불금 확인" → `REFUNDED`.
- **분쟁**: 소비자가 "문제가 해결되지 않았습니다" → `DISPUTED`. 관리자 화면: 주문번호, 판매자, 소비자, 상품, 결제금액, 분쟁사유, 사진, 판매자 답변, 관리자 메모.

## 23~26. 화면

- Seller: `/dashboard`, `/products`, `/products/new`, `/orders`, `/profile`. 상품 등록은 한 화면(① 기기정보 ② 상태 ③ 기능검사 ④ 가격 ⑤ 사진 ⑥ 판매등록).
- 소비자: `/`, `/products`, `/products/:id`, `/order/:id`, `/order/:id/payment`, `/orders/:id`
- 목록 필터: 제조사, 모델, 가격, 용량, 등급. 정렬: 최신순/낮은가격/높은가격.
- 상품 카드: [사진] / 모델 / 용량·색상 / 등급 / 배터리 / 가격 / 판매자. 정보를 많이 넣지 않는다.

## 27~36. DB 설계

`users`(role BUYER/SELLER/ADMIN), `sellers`(status PENDING/APPROVED/REJECTED/SUSPENDED), `products`, `product_images`, `product_inspections`(NORMAL/ABNORMAL/UNKNOWN), `orders`(주문 시점 가격 복사, reserved_until), `bank_transfer_reports`(실제 금융정보가 아닌 입금 상태 기록: buyer_reported_at, seller_confirmed_at), `shipments`, `refund_requests`, `disputes`, `audit_logs`(판매자/소비자의 "나는 버튼을 누르지 않았다" 분쟁 대비 — 주요 변경사항 모두 기록: user_id, action, entity, old/new, ip).

## 37~38. API

- 상품: `GET /api/products`, `GET /api/products/:id`, `POST/PUT/DELETE /api/seller/products(/:id)`
- 주문: `POST /api/orders`, `GET /api/orders/:id`, `POST /api/orders/:id/deposit-report`, `/cancel`, `/refund`
- 판매자: `GET /api/seller/orders`, `POST /api/seller/orders/:id/deposit-confirm`, `/shipping`, `/refund-complete`
- 관리자: `GET /api/admin/sellers`, `POST /api/admin/sellers/:id/approve|reject|suspend`, `GET /api/admin/products|orders|disputes`

## 39~41. 기술스택

Next.js + TypeScript + Tailwind, Next.js Server Actions/API, PostgreSQL(Supabase: Auth, Storage, DB), Vercel 배포. 초기 구조는 최대한 단순하게.

## 42~44. 보안 / 동시구매 / 가격 변경 방지

- 판매자 계좌는 주문 생성 전까지 소비자에게 노출 금지. 전체 IMEI 공개 금지. 소비자 주소는 해당 주문 판매자에게만. ADMIN Role 검증 필수(URL 직접 접근 차단).
- 중고폰 1대를 A와 B가 동시에 주문하면 안 된다: 상품 ON_SALE 확인 → RESERVED 변경 → 주문 생성을 하나의 트랜잭션으로.
- 주문 생성 시 `product.price`를 `orders.price`에 복사한다. 이후 판매자가 가격을 바꿔도 기존 주문가격은 불변.

## 45. MVP에서 만들지 않을 기능

결제(카드/네이버페이/카카오페이/토스페이), 경매/가격제안/공동구매/라이브커머스, 쿠폰/포인트/등급/멤버십, 후기/게시판/팔로우, AI 가격예측/검수, 자체배송/판매대금 정산/판매자 지갑. 전부 MVP 이후 판단.

## 46~48. 우선순위와 개발 순서

- **P0** (없으면 출시 불가): 소비자 상품목록·상세·주문·계좌정보 확인·입금완료·배송조회 / 판매자 가입·사업자인증·상품등록·주문조회·입금확인·배송처리 / 관리자 판매자 승인·상품조회·주문조회
- **P1**: 환불, 분쟁, 판매자 통계, 리뷰, SMS/카카오톡 알림. 단, 정식 공개 전에는 환불/분쟁을 P0 수준으로 올릴 것을 권장.
- 개발 순서: ① DB·Auth·판매자 회원가입·관리자 승인 → ② 상품등록·관리·목록·상세 → ③ 주문생성·RESERVED·계좌안내·입금완료·판매자 입금확인 → ④ 배송·구매확정 → ⑤ 취소·환불·분쟁

## 49~53. 성공 기준 / 대시보드 / KPI / 이후

- 성공: 판매자 10개 업체 입점, 업체당 상품 10개(총 100개), 실제 조회 → 주문 → 계좌이체 → 배송 → 거래완료 발생.
- 핵심 지표: 상품 상세조회 → 주문 전환율, 주문 → 실제 입금 전환율, 입금 → 거래완료율.
- 운영 대시보드 8개 숫자: 입점 판매자 수, 판매중 상품 수, 오늘 상품 등록 수, 주문 수, 입금완료 주문 수, 거래완료 수, 거래금액 GMV, 분쟁률.
- KPI: 공급(판매자 1명당 등록상품수), 수요(상세→주문 전환율), 거래(주문→입금률), 품질(취소율), 신뢰(분쟁률).
- 이후: 거래 데이터를 보고 카드결제 요구가 40%면 PG, 3%면 보류. Phase 2 평점/리뷰/등급/자동알림/시세비교/상품 일괄등록(Excel) → Phase 3 에스크로/PG/카드/간편결제 → Phase 4 AI 시세/설명 자동생성/사진 검수/가격 추천.

## 54~58. 원칙과 최종 개발 지시

처음부터 MSA, 정산 시스템, 판매자 지갑, Kafka는 필요 없다. Next.js + Supabase + Vercel로 충분하다. 플랫폼이 돈을 보관하지 않는 것이 핵심이다. MVP 성공 후 가장 먼저 추가할 기능은 PG가 아니라 판매자 상품 대량등록(Excel/API/ERP 연동)이다. 장기적으로 모델별·등급별·배터리별 실거래가, 등록→판매 소요시간, 판매자별 판매속도, 지역별 수요 데이터를 쌓아 "대한민국 중고폰 실거래 시세 DB"를 만든다.

**최종 개발 지시 — 이 한 사이클이 완성되기 전에는 다른 기능을 추가하지 않는다.**

> 판매자 1명이 가입하고 관리자가 승인한다. 판매자가 실제 아이폰 한 대를 등록한다. 소비자가 해당 아이폰을 보고 주문한다. 판매자의 계좌가 표시된다. 소비자가 실제로 송금한다. 판매자가 입금을 확인한다. 송장번호를 등록한다. 소비자가 배송상태를 확인한다. 주문이 거래완료 상태가 된다.
